| 2026-08-14 | (this commit) | **What counts as the "matched-lr arm" in `check_failure_claims`.** CLAUDE.md requires a failing rank cell to report "the matched-lr arm and the 10×-steps arm alongside it". The 10×-steps arm is unambiguous (h0₂). The matched-lr arm is not: with lr already swept independently per rank, I read it as *that sweep* — a rank may be called a capacity failure only if ≥3 distinct lr points at that rank all failed. That is a strictly stronger control than a single run at some reference lr, and it is what the grid already pays for. But it is a different object from what "the matched-lr arm" most literally names (one run at the lr that worked for the generous-rank reference), and if the intent was the literal reading, the gate as written would pass a claim that the literal reading would reject: three lr points clustered in a bad region all failing is not the same evidence as failing at the lr known to work. Confirm the reading before any M1/M2 failure is written up. |
| 2026-08-14 | (this commit) | **h0_3's matched-β control is a coordinate subspace, not a dense random one.** `nulls.matched_beta_support` pins all but β randomly-chosen *entries* of Δ*W* to zero. This matches β exactly and is fixed before training (§11's stated leaning), and the dense alternative is infeasible at these shapes (~9.7 GB, and β exceeds the ambient dimension at generous rank). But a coordinate subspace is not distributionally the same object as a dense Gaussian one: it is axis-aligned in the basis the weights happen to be stored in, so a Δ*W* whose useful directions align with coordinate axes is favoured, and one whose do not is penalised. If h0_3 comes back "the unstructured control performs identically", that conclusion is about *this* control. Nothing in the tests can distinguish "low-rank structure doesn't matter" from "the coordinate basis happened to be adequate". A human should confirm this is the intended control before M3/M6 run. |
| 2026-08-14 | (this commit) | **h0_4's separation band is a reading of §6, not a quotation of it.** §6 says h0_4 is falsified by "separation exceeding the matched-norm random-null band" without defining the band. `nulls.phi_separation_null_band` takes it as the 95th percentile of $\|\varphi_{QK} - \varphi_{OV}\|$ over *paired* independent matched-norm nulls — one draw per arm, each with its own shape and norm. The percentile reuses the repo's existing convention (G1, h0_6) rather than inventing one, and no threshold was edited. The alternative reading — two separate one-arm bands, asking whether the arms' bands overlap — is a different and generally *less* powerful test, and I cannot tell from §6 which was meant. Sign off before any M4/M6 row reports against it. |
| 2026-08-14 | 5d88030 | `train.py`'s LoRA hook injection (`qk_hooks`/`ov_hooks`) assumes TransformerLens's within-block hook execution order is stable (`ln1.hook_normalized` before `attn.hook_q`; `attn.hook_z` before `hook_attn_out`) so a "capture, then add" closure sees the right tensor.
